# Sub2Video 后台服务架构分析

> 本文档是**设计与选型分析**，不是实现清单。  
> 产品语义以 `docs/产品方案总览.md`、`docs/api/client-*.md` 为准。  
> 管理端 API 本期不展开，但表结构需预留扩展位。

---

## 1. 现状澄清

### 1.1 产品文档已定什么

| 层级 | 约定 |
| --- | --- |
| 前端 | Vue 3 mock，**尚未接 API** |
| 目标栈 | **Go + MySQL + Redis + OSS**（见产品方案总览） |
| 可复用 | Sub2API 的用户、认证、角色、钱包、订单、日志工程基础 |
| 客户端 API | `/api/v1/client/...`，见 `docs/api/` |
| 管理端 API | `/api/v1/admin/...`，本期不做 |

### 1.2 仓库里已有什么（需正视）

`backend/` 下有一段**过早落地的原型代码**，与目标架构差距很大：

| 项目 | 原型现状 | 目标 |
| --- | --- | --- |
| Web 框架 | **chi**（不是 Gin） | 待定：Gin / chi / 复用 Sub2API 现有栈 |
| 数据库 | **SQLite 单文件（已废弃原型）** | **PostgreSQL**（与 Sub2API 统一） |
| 缓存/队列 | 无 | **Redis**（任务状态、限流、队列） |
| 对象存储 | 无，缩略图写死 URL | **OSS**（上传素材、成片、签名下载） |
| 认证 | 固定 `Bearer dev-token` | **登录/注册/JWT/刷新令牌** |
| 支付 | 模拟充值入账 | 微信等支付通道 + 回调 |
| Provider | 内置 goroutine 模拟进度 | 真实 MiniMax H3 调度层 |
| 表结构 | JSON  blob 塞作品树 | **规范化 MySQL 表** + 必要 JSON 扩展字段 |

**结论：** 这段原型可用于「接口形状试通」，不应作为正式后台基础；应先完成本分析，再按阶段重写或对齐 Sub2API。

## 2. 你问的三个直接问题

### 2.1 用的 MySQL 和 OSS 吗？

**没有。** 原型只有 SQLite，没有 OSS SDK，文件上传只记了一条 `uploads` 元数据，没有真实存储。

按产品方案，正式环境应是：

```text
PostgreSQL → 用户、钱包、订单、任务、作品元数据、工单、定价快照
Redis      → 任务队列、进度缓存、会话/限流、分布式锁
OSS        → 用户上传首帧、生成结果 mp4、作品工程内文件
             （客户端只见「容量/有效期」，不见 Bucket）
```

已确认决策（2026-09-03）：

- **数据库统一 PostgreSQL**（与 Sub2API 对齐，降低认证/支付移植成本）
- **框架对齐 Gin**
- **从 Sub2API 按需提取**平台层，不整体 fork
- OSS：MinIO（S3 兼容）UAT，生产可换阿里云 OSS

### 2.2 框架用的 Gin 吗？

**不是，原型用的是 [chi](https://github.com/go-chi/chi)。**

选型对比（Sub2Video 场景）：

| 框架 | 优点 | 缺点 | 建议 |
| --- | --- | --- | --- |
| **Gin** | 生态最大、示例多、中间件丰富 | 偏「框架感」，与 Sub2API 若不一致则难复用 | 若 **新建独立服务** 且团队熟悉 Gin，可选 |
| **chi** | 轻量、标准库风格、路由清晰 | 需自己拼装更多中间件 | 适合薄 HTTP 层 + 清晰分层 |
| **复用 Sub2API 底座** | 认证/钱包/用户已有 | 需改造边界，不能暴露 API Key 模型 | **产品文档首选路径** |

**推荐顺序：**

1. 先评估 Sub2API 能否 fork/内嵌用户与钱包模块（不修改其外部 worktree，按 AGENTS.md 在 sbu2video 仓库内引入或复制接口层）。
2. 若独立新建：`Gin` 或 `chi` 均可；**选与 Sub2API 一致的**，减少两套中间件。

### 2.3 登录呢？

**完全没有。** 这是当前最大缺口。

前端已有 Auth 页面（登录/注册/验证/忘记密码），但：

- 无 `POST /api/v1/auth/login` 等接口
- 无用户表密码哈希、邮箱验证、刷新令牌
- 客户端 API 文档默认 `Authorization: Bearer <token>`，未定义签发方式

必须在**第一期后台**就包含认证域，否则无法多用户、无法上 UAT。

## 3. 目标架构（逻辑视图）

```text
                    ┌─────────────┐
  Browser ──12000──►│ Nginx (107) │
                    │  / → SPA    │
                    │  /api → Go  │
                    └──────┬──────┘
                           │
              ┌────────────┴────────────┐
              ▼                         ▼
     ┌─────────────────┐      ┌──────────────┐
     │  API Server     │      │  Worker      │
     │  (HTTP)         │      │  (异步任务)   │
     └────────┬────────┘      └──────┬───────┘
              │                      │
    ┌─────────┼─────────┬────────────┼────────┐
    ▼         ▼         ▼            ▼        ▼
  MySQL    Redis      OSS      Provider   支付回调
 (事务)   (队列/缓存) (文件)   (MiniMax)  (微信)
```

### 3.1 服务拆分建议

| 进程 | 职责 | 首期是否独立部署 |
| --- | --- | --- |
| `api` | HTTP：认证、客户端 API、支付回调、上传签名 | 是 |
| `worker` | 消费 Redis 队列：调 Provider、更新进度、写 OSS | 可与 api 同进程，后期拆分 |
| `migrate` | 数据库迁移 Job | CI / 发布时一次 |

## 4. 107 部署与端口规划（避免冲突）

### 4.1 当前 107 已知

| 服务 | 端口 | 说明 |
| --- | --- | --- |
| Nginx 静态前端 | **12000** | 已用，`deploy/sub2video-uat.nginx.conf` |
| 后台原型配置 | **8080** | ⚠️ 易与机器上其他服务冲突 |

### 4.2 推荐做法

**原则：后台端口不对外暴露，只给本机 Nginx 反代。**

| 方案 | 配置 | 说明 |
| --- | --- | --- |
| **A（推荐）** | Go 监听 `127.0.0.1:12080` | 与前端 12000 同系列，不易冲突 |
| B | Unix socket `/run/sub2video/api.sock` | 完全无 TCP 端口冲突 |
| C | Docker compose 内网 | `api:8080` 仅 bridge 网络 |

Nginx 片段（方案 A）：

```nginx
location /api/ {
    proxy_pass http://127.0.0.1:12080;
    # ...
}
```

环境变量：`SUB2VIDEO_ADDR=127.0.0.1:12080`

**不要在 107 上本地启动调试**；应 CI/本机构建 Linux 二进制 → scp → systemd 拉起。

## 5. 认证域设计（补缺）

### 5.1 接口（建议）

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/api/v1/auth/register` | 邮箱 + 密码 |
| POST | `/api/v1/auth/login` | 返回 access + refresh |
| POST | `/api/v1/auth/refresh` | 刷新 access |
| POST | `/api/v1/auth/logout` | 作废 refresh（Redis 黑名单） |
| POST | `/api/v1/auth/forgot-password` | 发邮件 |
| POST | `/api/v1/auth/reset-password` | 重置 |
| POST | `/api/v1/auth/verify-email` | 验证链接 |

客户端/管理端：**不同 audience 的 JWT claim**（`aud=client|admin`），或分开发 `{client,admin}_refresh_token`。

### 5.2 安全要点

- 密码：`bcrypt` 或 `argon2id`
- Access Token：15–30 分钟 JWT
- Refresh Token：7–30 天，存 Redis 可撤销
- 管理端：独立角色（RBAC），与创作者隔离

### 5.3 开源替代（认证）

| 组件 | 用途 | 备注 |
| --- | --- | --- |
| [Casdoor](https://github.com/casdoor/casdoor) | 完整 IdP（登录页也可托管） | 偏重，适合快速有账号体系 |
| [Keycloak](https://www.keycloak.org/) | 企业级 IdP | 运维成本高 |
| [golang-jwt/jwt](https://github.com/golang-jwt/jwt) + 自研 | 轻量 JWT | 与 Sub2API 一致时优先 |
| [casbin](https://github.com/casbin/casbin) | RBAC/ABAC | 管理端权限 |

若 Sub2API 已有用户表与登录逻辑，**优先复用**，Sub2Video 只加 `workspace`、创作者扩展字段。

## 6. MySQL 表结构设计（首期可用 SQLite 跑迁移）

设计原则：

- 主键：`BIGINT` 自增或 `CHAR(26)` ULID（对外 API 仍用 `tsk_*` 等友好 ID 字段）
- 金额：`DECIMAL(12,2)`，不用 float
- 时间：`DATETIME(3)` UTC 存库，API 出 ISO 8601
- 软删：`deleted_at` 仅用于用户/作品等；任务用状态机
- 作品目录：**元数据表 + `path`/`parent_id`**，避免整棵树 JSON（便于检索与配额统计）

### 6.1 用户与认证

```sql
-- 用户
CREATE TABLE users (
  id            BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT,
  public_id     VARCHAR(32) NOT NULL UNIQUE COMMENT '对外 u_*',
  email         VARCHAR(255) NOT NULL UNIQUE,
  password_hash VARCHAR(255) NOT NULL,
  display_name  VARCHAR(64) NOT NULL,
  status        ENUM('active','frozen','pending') NOT NULL DEFAULT 'pending',
  email_verified_at DATETIME(3) NULL,
  created_at    DATETIME(3) NOT NULL,
  updated_at    DATETIME(3) NOT NULL,
  deleted_at    DATETIME(3) NULL,
  INDEX idx_users_status (status)
);

-- 工作区（创作者工作室，1:1 首期）
CREATE TABLE workspaces (
  id            BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT,
  user_id       BIGINT UNSIGNED NOT NULL UNIQUE,
  name          VARCHAR(128) NOT NULL,
  created_at    DATETIME(3) NOT NULL,
  FOREIGN KEY (user_id) REFERENCES users(id)
);

-- 刷新令牌（也可只放 Redis）
CREATE TABLE refresh_tokens (
  id            BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT,
  user_id       BIGINT UNSIGNED NOT NULL,
  token_hash    CHAR(64) NOT NULL UNIQUE,
  expires_at    DATETIME(3) NOT NULL,
  revoked_at    DATETIME(3) NULL,
  created_at    DATETIME(3) NOT NULL,
  INDEX idx_rt_user (user_id),
  FOREIGN KEY (user_id) REFERENCES users(id)
);
```

### 6.6 SQLite 开发期注意

- 用 `golang-migrate` 或 `goose` 维护迁移；枚举用 `TEXT` + CHECK 约束
- `DECIMAL` 在 SQLite 用 `TEXT` 存字符串或整数分（cents）统一
- **不要**在 SQLite 阶段用 JSON 树代替 `project_nodes`，否则迁 MySQL 要重写

## 7. 开源组件替代清单（汇总）

按层分类，**优先用成熟组件，少写基础设施**。

| 层次 | 推荐开源 | 替代什么 |
| --- | --- | --- |
| HTTP 路由 | Gin / chi / Echo | 自写路由 |
| 配置 | [viper](https://github.com/spf13/viper) | 环境变量散落 |
| 日志 | [zap](https://github.com/uber-go/zap) / slog | 标准 log |
| 迁移 | [golang-migrate](https://github.com/golang-migrate/migrate) | 手写 DDL |
| ORM / SQL | [sqlc](https://github.com/sqlc-dev/sqlc)（推荐）或 GORM | 手写 SQL 拼接 |
| 校验 | [go-playground/validator](https://github.com/go-playground/validator) | 手写参数检查 |
| JWT | [golang-jwt/jwt](https://github.com/golang-jwt/jwt) | dev-token |
| 密码 | golang.org/x/crypto/bcrypt | 明文 |
| Redis 客户端 | [go-redis](https://github.com/redis/go-redis) | 无 |
| 任务队列 | [hibiken/asynq](https://github.com/hibiken/asynq) | goroutine 模拟 |
| 限流 | [ulule/limiter](https://github.com/ulule/limiter) | 无 |
| OSS | [minio-go](https://github.com/minio/minio-go) 或阿里云 OSS SDK | 假 URL |
| 上传 | 预签名 PUT + 直传 OSS；大文件可加 [tusd](https://github.com/tus/tusd) | multipart 进 API |
| ID | [oklog/ulid](https://github.com/oklog/ulid) | 自增序列 |
| 邮件 | [go-mail](https://github.com/wneessen/go-mail) + SMTP | 无验证邮件 |
| 支付 | 微信支付官方 Go SDK | 模拟充值 |
| 可观测 | OpenTelemetry + Prometheus | 无监控 |
| API 文档 | swaggo/swag 或 OpenAPI 手写 | 仅 markdown |
| 集成测试 | testcontainers-go | 手搓 SQLite |

**不建议从零写的：** 认证、队列、迁移、OSS 签名、支付验签。

## 9. 107 部署检查单（实施 P1 时用）

1. 本机 `GOOS=linux GOARCH=amd64 go build` 交叉编译
2. 上传至 `/opt/sub2video/backend/`，**监听 `127.0.0.1:12080`**
3. systemd：`deploy/sub2video-backend.service`（改端口环境变量）
4. Nginx：`proxy_pass http://127.0.0.1:12080`（改自 8080）
5. PostgreSQL：107 上 Docker（建议宿主机映射 `127.0.0.1:15432`，避免与已有 5432 冲突）
6. Redis / MinIO：内网端口不映射公网（或仅绑 `127.0.0.1`）
7. 部署前 `ss -lntp` 确认端口占用
