## 1. 结论

当前代码已经有可保留的产品基础，主要问题是几轮业务和视觉改造叠加后，没有及时收敛旧实现、状态所有权、文档与验证入口。继续增加导演台会把这些问题带入多镜头流程，应先完成一轮有边界的整理。

最需要先解决的不是文件夹是否漂亮，而是：

1. 用户切换后，创作草稿和业务缓存缺少完整隔离。
2. 供应商配置的新旧表双写缺少事务边界。
3. 类型检查命令可以检查零个文件却成功退出，浏览器测试还有时序不稳定。
4. 当前业务已经不使用 quote，但正式文档、旧函数和部分类型仍保留另一套理解。
5. 生产部署目录保留能直接改钱包并输出登录响应的历史脚本。

不建议更换 Vue/Go 技术栈、改微服务、重新建一套设计系统，或一次性删除旧表。建议保留现有合同，先修具体问题，再小步调整职责。

## 3. 应当保留的基础

- 正式路由已经是 `POST /client/tasks/estimate` 和 `POST /client/tasks`；旧 quote 接口明确返回 410。不能因为源码还存在旧函数，就说当前客户端仍在消费 quote。
- `CreateTaskDirect` 在事务内先检查用户和请求 ID 对应的原订单，再进行路由与扣款；重复请求的恢复顺序值得保留。
- Worker 使用任务执行快照；不明确的上游提交结果进入核对流程，不能在整理时改成自动重提或退款。
- 创作页已有估价/能力请求序号、上传/提交锁定、按用户保存的待确认提交记录。普通草稿的隔离问题不代表待确认订单记录也未隔离。
- 资产、概览、交付已有 feature/composable 分层，可以直接作为创作页和管理端整理的本地范例。
- 已有桌面/窄屏交互测试、视觉基线和单独的数据库集成测试入口。需要提高可信度，不必另起一套测试体系。

## 5. 为什么维护起来会感觉混乱

### 5.1 三代业务概念仍在同一层

当前正式路径是 execution + estimate/direct submit，但仓库同时保留旧 workflow 创建、quote 创建/消费、offering/route 与 execution 桥接。

具体表现：

- [tasks.go](../../backend/internal/store/tasks.go) 的旧 `CreateTask`、[creation_catalog.go](../../backend/internal/store/creation_catalog.go) 的 `CreateQuote/CreateTaskFromQuote`，以及旧 pricing/routing 包没有现行生产调用；它们的单测不能替代正式 `ResolveDirectRoute` 验证。
- 新提交为了复用素材校验仍构造临时 `TaskQuote`；执行标识还借用 `Offering.ID` 和 `supplier_route_id`。这是旧类型残留，不是新流程重新锁价。
- Worker 解码新旧快照时有多层 fallback，权威字段不够直观。
- 管理端 `AdminOffering` 同时携带 `executionId`、`upstreamWorkflowId`、`workflowCode`，成本又兼容 offering/execution 两套 ID。

整理方法：先列出“入口、调用者、表、测试、历史读取用途”，再删除已证明不可达的业务入口。新旧 DTO 的转换集中在一个边界；可先在同一 Go 包内拆文件，不必新增 service/RPC。迁移、历史任务快照和数据库表不能仅因名字旧就删除。

### 5.2 同一规则由多个地方维护

- 目录、模型选项、推荐、首页参考价格、正式路由各自维护供应商/模型状态、健康、额度、成本有效期等过滤 SQL。
- 目录的“有凭据密文”与提交时的“能解密并具备存储”不是同一个可用性层级，需要明确说明，而不是机械要求所有接口做同样重活。
- 用户取消、管理员取消、上游失败分别维护退款 SQL。现有事务和状态检查不能随拆分被破坏。
- 部分数据库错误被当成候选不匹配而跳过，可能把基础设施故障表现为“暂无供给”。

整理方法：共享有限范围的候选筛选规则、事务内退款 helper、快照解码与稳定错误码。权限、租约和状态前置检查仍由各入口负责。不要为几条规则建立通用规则引擎。

### 5.3 页面拆了外观，业务编排仍很集中

| 文件 | 当前总行数（含空行） | 主要集中职责 | 适合的拆分方式 |
| --- | ---: | --- | --- |
| `backend/internal/store/creation_catalog.go` | 1,751 | 目录、能力、价格、旧报价、管理配置和兼容查询 | 先分目录读取/执行配置写入/历史兼容；保持事务边界 |
| `backend/internal/handler/admin.go` | 1,070 | 多类管理接口 | 按现有管理资源移动函数，复用错误和分页入口 |
| `frontend/src/pages/client/CreatePage.vue` | 859 | 素材、目录、估价、提交恢复、草稿、教程、预览 | 逐步提取素材、估价、提交恢复、草稿编排；页面保留布局 |
| `frontend/src/pages/admin/SupplierModelsPage.vue` | 531 | 多 tab、目录/计数加载、分页、配置编辑、成本保存 | 分离共享目录、当前 tab 数据与编辑器；避免一个非当前 tab 请求失败拖垮整页 |

这些行数是定位线索，不是拆分指标。`PricingPage.vue` 已较小，资产和交付也已有明确边界，无需为目录整齐继续重构。

创作页的 `loadCreationCatalog`、watch、教程应用都可能触发 options 请求；请求序号防住旧响应，但重复副作用仍增加调试难度。供应商页翻页还会重新读多类目录和逐行子列表，应把加载所有权整理清楚。

### 5.4 可达占位与不可达旧代码没有分清

- 当前可达的 Profile 占位影响真实体验，应优先处理。
- `ProvidersPage.vue` 无现行路由，`/admin/providers` 已跳转新页面；Users、Products、Announcements、Orders 等旧页也不在当前路由中。
- `CreateModeGate`、`CreateModeCards`、`ImageStack` 及其专属子组件、`SceneCard`、`data/scenes.ts` 在当前静态引用中不可达。
- `data/projects.ts` 包含当前在用类型/函数，不能因为目录名是 data 就当 Mock 删除。
- Worker 每轮仍推进 `execution_mode='simulated_legacy'` 的任务；它有隔离条件，不证明真实 provider 任务会假成功。模拟任务的历史政策应先确定，再移出正式 Worker 默认职责。

清理应独立成包：证明不可达、删除专属代码、运行相关合同与视觉测试。不能顺手删除整个 data、旧 store 或历史表。
