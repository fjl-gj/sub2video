# 导演台首版：镜头编排与候选选片

日期：2026-10-05。基于现有作品、创作、任务、素材和钱包合同实现；视觉仍遵循 [design-system.md](./design-system.md)。

## 本轮解决的问题

单次创作已有任务与交付记录，但一个作品的多个镜头缺少顺序、意图和候选选片关系。用户容易丢失“这次生成属于哪个镜头、最后采用哪一版”的上下文。

本轮采用 Toonflow 的“准备素材 → 生成 → 查看历史候选 → 采用当前结果”场景，在 Sub2Video 中实现原生页面。并非嵌入 Toonflow 服务、画布或节点引擎；不建立第二套账户、供应商与计费系统。来源及许可边界见 [接入记录](../engineering/toonflow-integration-2026-10-05.md)。

## 入口与页面关系

入口在资产页所选作品内，路由为 `/app/projects/:projectId/director`。不增加一级导航，不改变作品与目录的含义。

```text
资产 / 当前作品 → 导演台
                    ├─ 镜头顺序、名称、画面描述
                    ├─ 保存镜头板 / 导出清单
                    ├─ 前往创作 → 显式应用镜头 → 素材、参数 → 保存到镜头（不生成、不扣费）
                    │                                    └─ 估价、提交 → 任务详情 → 返回导演台
                    └─ 已有任务候选 → 查看真实状态 → 采用已交付版本
                                               └─ 下载 / 保存到作品（任务详情）
```

桌面工作区：左侧镜头顺序，中间镜头描述，右侧候选结果。窄屏按“镜头 → 描述 → 候选”顺序排列，不能挤成三个狭窄表单。根据可用内容宽度折叠，沿用外层对齐轴与底部导航留空。

标题、按钮、表单和弹窗复用既有共享组件；领域布局和样式由导演台 feature 持有。没有装饰性 AI 徽章、虚构成片、示例收入或新品牌皮肤。

## 可操作范围

- 新增、排序、编辑、移除镜头；明确保存，未保存离开时提示。
- 不完整镜头允许保存，不要求先选模型或先有供给。
- 候选关联现有任务 ID；选择最终版本只允许已成功且实际交付就绪的任务。
- 删除镜头只删除编排关系，不取消任务、不退款、不删除素材。
- 进入创作不会自动覆盖普通草稿或自动提交；显式应用后使用隔离的镜头草稿。
- 创作页可把描述、素材和公开参数独立“保存到镜头”，本地图片先上传再保存引用；不依赖余额或估价成功，不创建任务、不扣费。
- 保存镜头期间冻结相关操作。版本冲突或保存结果不确定时保留本地草稿，必须重新读取并明确应用后再保存，不能反复覆盖旧板。
- 创作提交继续由既有能力目录和估价决定可用参数，不能静默替换用户指定模型。
- 导出 JSON 镜头清单，包含顺序、参数与选片引用，不包含签名下载地址或供应商字段。导出不是视频拼接。

暂不包含：剧本自动拆分、人物一致性生成、画布连线、剪辑时间线、字幕配音、全片合成、批量自动付费或 Toonflow 节点执行。

## 数据合同

复用 `projects`，迁移 `022_project_director_board.sql` 添加 `director_board` 与 `director_revision`。镜头数量限 100，每镜头候选限 20，板请求限 1 MiB。

| 接口 | 用途与边界 |
| --- | --- |
| `GET /client/projects/:id/director-board` | 读取当前用户未回收作品的镜头板 |
| `PUT /client/projects/:id/director-board` | `expectedRevision + shots` 乐观并发保存；冲突返回 409，保留本地编辑 |
| `POST /client/projects/:id/director-board/shots/:shotId/candidates` | 手工关联当前用户已有任务；重复关联幂等，不创建新任务 |
| `POST /client/tasks` 的可选 `directorContext` | `{ projectId, shotId, expectedRevision }`；同事务创建任务并关联镜头 |

镜头保存公开参数与素材 ID、候选任务 ID 和选中任务 ID，不保存上游路径、执行编码、成本或凭据。后端验证作品/素材/任务归属；仅客户端隐藏字段不能代替权限检查。

## 原子性与恢复

提交顺序必须为：请求幂等锁与原订单查询 → 作品锁与镜头版本校验 → 原有路由/钱包/订单/任务创建 → 关联候选及保存实际输入 → 提交事务。不能先扣费再用独立请求关联镜头。

已成功请求的重放必须先返回原订单与任务，不受镜头后来删除、版本变化或供应商下线影响。网络结果不确定时保留原请求 ID、完整 payload 与 directorContext，不能换 ID 自动重试。

镜头板并发保存失败时保留本地编辑，提供导出与重新加载。后台提交新增候选会递增 revision，旧页面不能通过整板保存静默覆盖新候选。

## 验收边界

| 层次 | 必须验证 | 能证明什么 |
| --- | --- | --- |
| Go 单元测试 | DTO、边界与错误分类 | 局部规则 |
| 隔离 PostgreSQL/Redis | 重复迁移、归属、并发版本、事务回滚、成功请求重放 | 数据与计费原子性；缺环境时明确未验证 |
| 浏览器 API Mock | 保存刷新、409 保留、草稿保护、候选状态、提交冻结 | 前端交互合同，不证明真实数据库或生成成功 |
| 视觉与尺寸 | 320 / 390 / 768 / 1024 / 1440 / 1920 px；桌面和手机审图 | 布局与可操作性，不证明业务后端 |
| 真实环境 | 部署 022 后的归属、持久化和已有任务关联 | 本轮不部署；不能沿用旧 UAT 成功作新功能证据 |
